# Reports and backup operations

## Reports

Open **Analytics & reports / التحليلات والتقارير** in the application navigation. The dashboard reports only data actually stored by the current customer module:

- Customer directory (all currently implemented customer fields, embedded contacts, dates and local sync status).
- Customers grouped by governorate/city.
- Customers grouped by type/classification.
- Customer activity history.
- Visits and meetings (activity-log entries of those types).
- Calls and follow-ups (activity-log entries of those types).

An activity such as “sale” or “collection” is a descriptive activity-log entry only; it is not a sales/collection transaction report. Reports do not invent data for the placeholder sales, collection or quotation modules.

Filters include inclusive local date-range selection (start and end calendar days), governorate, city, customer type, classification, activity type, and archive status. The date interval is `[start, day-after-end)`: customer reports filter by customer creation time; activity reports filter by activity occurrence time. “All records” deliberately ignores the selected filters; otherwise, current filters are applied. The preview is limited to 20 rows; exported results are not truncated.

Each XLSX contains `Records` and `Report` worksheets. The records sheet has a frozen header, AutoFilter, RTL sheet direction for Arabic, typed date/number cells, suitable widths, and a summary with the generation timestamp, result-row count, matched-record count, and selected filters. Arabic/English headers follow the selected application language.

PDF output is A4, uses the navy-and-white Target identity, embeds the bundled Amiri fonts, follows the selected RTL/LTR direction, includes filters, counts and page numbers, and paginates report rows. Both formats are generated as local bytes and handed to the existing Android/Windows save dialog (and the browser download on Web). A save-dialog cancellation is not reported as success.

## Backup and restore

Open **Backup / النسخ الاحتياطي**. Create a portable JSON backup and select a destination in the platform save dialog; the screen confirms the generated filename, UTC date and byte size. Restore by selecting a previously exported JSON file. The review dialog shows the checked timestamp/counts before confirmation.

An empty-database restore never merges. Replacing existing data is a separate explicit action and proceeds only after the safety-copy save is acknowledged. Validation, version checks, staging, final fingerprint check and transactional writes prevent silent overwrite and leave current data intact on failure. No merge or backup history is offered. See [PORTABLE_BACKUP_FORMAT.md](PORTABLE_BACKUP_FORMAT.md) for the portable interchange contract and limitations.

## Verification limits

CI runs Flutter unit/widget/export tests; saves actual Arabic and English XLSX/PDF fixtures; parses every workbook with `openpyxl`; validates XLSX structure and metadata; parses each PDF with PyMuPDF and rasterizes every A4 page; and runs portable-backup recovery tests against a native database on Windows using a backup generated by the Linux test job. The reports and PDFs contain synthetic test fixtures only.

Android debug/release and Windows Release builds, Android native document-writer JVM tests, and Windows native IO tests are separate build/native checks. This is not an interactive Android-device installation or save-dialog test. Visual review on actual Microsoft Excel, Acrobat, a physical Android device, and a Windows desktop remains a controlled QA task; generated PDF page geometry, embedded fonts, extracted text, and rasterization checks are not a substitute for that review. Production Android signing is not configured.
