## Decisions and dependency footprint

Feature-based Clean Architecture boundaries, constructor composition and built-in
Flutter state/navigation keep the initial dependency footprint minimal. Domain/data
contracts are deliberately not invented before business requirements exist.
Runtime dependencies are only `flutter` and SDK `flutter_localizations`.
Development dependencies are SDK `flutter_test` and `flutter_lints ^6.0.0`.
No database, synchronization service or paid backend is integrated.

Arabic-first localization supports English and RTL/LTR; desktop uses a sidebar and
mobile/tablet a drawer. No real or fictitious customer/financial dataset is included.
Forms and tables have centralized theme defaults but no business implementations.

## Platform provenance and release caveats

Scaffolds were rendered from official Flutter **3.38.5** commit
`f6ff1529fd6d8af5f706051d9251ac9231c83407`, not generated by a locally running SDK.
Versions follow that template: Gradle 8.14, Android Gradle Plugin 8.11.1,
Kotlin 2.2.20. The original template license is retained. Missing binary image
placeholders were replaced by deterministic navy/white monograms and launch images.

All five platform builds are **unverified locally**. Windows requires Windows
with Visual Studio desktop C++; iOS/macOS require macOS/Xcode. Android needs its
SDK/JDK. Signing, application-ID ownership, store metadata, installers and
production branding require later review. Android release currently retains the
standard template's debug signing configuration, not production release signing.

## Known limitations / remaining work

1. No Flutter/Dart SDK here: resolve dependencies, commit `pubspec.lock`, run Dart
   formatting, analysis, tests and build gates on a supported host.
2. No native platform runtime verification; complete the manual device matrix.
3. Session-only locale/navigation; no deep links/browser history or persistence.
4. No operational business logic, storage, backend, auth, permissions or sync.
5. No data-entry screens, sales tables, Excel/PDF or production reports yet.
6. Review Arabic typography/accessibility on target devices; platform fallback
   fonts are used rather than downloading external fonts.

## Recommended Phase 2

First close the verification gates. Then agree on customer fields, identity,
currency/amount/date policies, data ownership and offline/backup requirements.
Implement one tested vertical slice: customer domain model and validation,
repository contract, local persistence with migrations, use cases, controller,
responsive list/form and localized error states. Evaluate a free local database
against all platforms before selection. Establish stable IDs and a future sync
strategy without introducing a cloud dependency. Extend the same patterns to the
remaining modules only after that slice is accepted.
